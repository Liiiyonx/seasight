# 系统架构与数据流详解

> 本文回答一个问题：**从摄像头拍到一片泡沫，到机器人把它捞上来，数据在系统里走了哪几个来回。**

---

## 一、为什么是这个架构

### 1.1 一个必须先说清楚的取舍

市面上多数"智能清洁船"方案，本质是**单机产品**：船上装摄像头，船上做识别，船上做打捞。这套逻辑的天花板很低——覆盖半径等于机器人的续航半径，一片海面要覆盖多少台？

探海灵眸的架构反过来：**感知在岸上、决策在云上、执行在水上**。

| | 单机方案 | 探海灵眸 |
| --- | --- | --- |
| 感知范围 | 机器人视野（几十米） | 岸基摄像头阵列（数公里） |
| 决策依据 | 眼前这一片 | 全辖区热力图 + 历史规律 |
| 扩展方式 | 买更多船 | 加摄像头 / 加机器人，两侧独立扩 |
| 数据沉淀 | 清理量一个数字 | 事件时空分布、类别构成、处置时长 |

这不是"做得更复杂"，而是**把单点产品做成区域级基础设施**——这才是政府部门会采购的东西。

### 1.2 平台是中枢，不是显示屏

最常见的做法是把平台做成"视频墙 + 弹框"。本项目明确不走这条路：

> **识别到垃圾不是弹框，而是产生事件 → 触发派单 → 形成可追溯工单。**

这个判断决定了数据库设计：**核心表是 `t_event`（事件表）与 `t_task`（工单表），不是视频表**。视频只是证据，事件才是业务对象。

## 二、分层结构

```
┌────────────────────────────────────────────────────────────────────┐
│ 展示层                                                              │
│   实时监测大屏 · 热力图 · 工单看板 · 报表中心 · 设备管理 · 移动端    │
├────────────────────────────────────────────────────────────────────┤
│ 接口层  app/api/v1/                                                 │
│   auth · events · tasks · devices · robots · stats · reports · ws   │
│   knowledge（资产 / 本体 / 检索 / 决策）· agents                   │
│   （只做参数校验与编排，业务逻辑一律下沉到 services）                │
├────────────────────────────────────────────────────────────────────┤
│ 应用层  app/services/                                               │
│   事件服务 · 派单引擎（五步筛选 + 防抖 + 状态机）· 后台消费者         │
│   知识资产、本体生命周期、多跳检索与决策轨迹                         │
├────────────────────────────────────────────────────────────────────┤
│ 智能层                                                              │
│   AI 推理服务（YOLO11 + ONNX/TensorRT）· 时序校验 · 误报过滤         │
├────────────────────────────────────────────────────────────────────┤
│ 数据层                                                              │
│   PostgreSQL 14 + PostGIS · Redis 7 (Streams) · MinIO · EMQX 5      │
├────────────────────────────────────────────────────────────────────┤
│ 接入层                                                              │
│   RTSP 流接入 · 边缘盒 MQTT 上报 · 机器人遥测 · 无人机巡查           │
└────────────────────────────────────────────────────────────────────┘
```

### 代码目录与层的对应关系

| 层 | 目录 | 硬规则 |
| --- | --- | --- |
| 接口层 | `backend/app/api/v1/` | 不写 SQL、不写业务分支；只做编排 |
| 应用层 | `backend/app/services/` | 不直接写 SQL，通过 repository 访问数据 |
| 数据访问层 | `backend/app/repositories/` | 只写查询，不含业务判断 |
| 模型层 | `backend/app/models/` | 只定义表结构与常量，不含逻辑 |
| 接入层 | `backend/app/mqtt/` | handler 自己开会话，不持有请求级 session |
| 领域认知层 | `backend/app/services/knowledge.py` + `integrations/nexent/` | 认知能力只走 HTTP/API 契约；机器人不是依赖 |

**为什么坚持这个分层**：派单逻辑会被三个入口调用（MQTT 上行、HTTP 备用通道、定时补派）。如果逻辑写在接口层，三处必然出现三份略有差异的实现——这是这类项目最典型的技术债。

领域认知层是追加能力，不改变 `t_event` / `t_task` 的业务语义。知识资产、
本体、检索和决策轨迹可在机器人离线时独立使用；事件、派单、机器人和 MQTT
链路仍是原有的可选执行端。

## 三、五个软件子系统

| 子系统 | 运行位置 | 责任组 | 代码位置 |
| --- | --- | --- | --- |
| 边缘感知软件 | 岸基摄像头旁的计算盒 | 算法组 | `edge/` |
| 机载软件 | 打捞机器人船载单元 | 硬件组 + 算法组 | `edge/robot/` |
| 数据平台 | 服务器 / 云 | 平台组 | `backend/` + `frontend/` |
| 模型训练管线 | 云端 GPU | 算法组 | `ml/` |
| AI 推理服务 | 与平台同机 | 算法组 + 平台组 | `backend/app/services/ai/` |

**组间接口是本文档定义的四条数据流**——只要流不破，三组可以并行开发，互不阻塞。这是备赛期并行推进的前提。

## 四、四条数据流

### 4.1 总览

```
  ┌──────────┐  ①RTSP    ┌──────────┐  ①HTTP-FLV  ┌──────────┐
  │ 摄像头    │ ────────► │ go2rtc   │ ──────────► │ 前端播放器│
  └────┬─────┘           └──────────┘             └──────────┘
       │ ②旁路取流
       ▼
  ┌──────────────┐  ③MQTT QoS1   ┌──────────────────────┐
  │ 边缘盒        │ ────────────► │  平台（FastAPI）      │
  │ YOLO+时序校验 │               │  事件服务→派单引擎    │
  └──────────────┘               └───────┬──────────────┘
                                         │ ④MQTT QoS1
                                         ▼
                                 ┌──────────────┐
                                 │ 打捞机器人    │
                                 └──────┬───────┘
                                        │ ⑤MQTT 回传 + 影像上 MinIO
                                        ▼
                                  （回到平台，闭环）
```

### 4.2 正文

| # | 数据流 | 方向 | 协议 | QoS / 要求 |
| --- | --- | --- | --- | --- |
| ① | 视频流 | 摄像头 → go2rtc → 前端 | RTSP → HTTP-FLV / WebRTC | 实时性优先，可丢帧 |
| ② | 旁路取流 | 摄像头 → 边缘盒 | RTSP 拉流 | 独立连接，不影响转发 |
| ③ | 检测事件流 | 边缘盒 → 平台 | MQTT | **QoS1**（必须送达，幂等去重） |
| ④ | 调度指令流 | 平台 → 机器人 | MQTT | **QoS1**（含 ACK 确认） |
| ⑤ | 作业回传流 | 机器人 → 平台 | MQTT + MinIO | 遥测 QoS0，结果 QoS1 |

### 4.3 一个容易被质疑的工程判断：**视频流不经过边缘盒**

初版设计很容易写成"摄像头 → 边缘盒 → 平台 → 前端"。这在这里是错的，原因是算力：

- 边缘盒的核心任务是**推理**，一张 1080p 图跑 YOLO11s 在中端算力盒上约 30~60ms
- 若要同时转发视频流，单路 4Mbps 的转发 + 解复用会持续占用 CPU 与内存带宽
- 结果是**推理帧率被转发挤下去**，而推理帧率恰恰是这套系统唯一的实质产出

所以设计成：**go2rtc 直接拉摄像头 RTSP 并转发给前端；边缘盒独立拉一路 RTSP 做推理。** 两条链路互不干扰，任何一条断掉都不影响另一条。

代价是摄像头要支持多路并发拉流——这是当前绝大多数 IP 摄像头都具备的能力（主流型号支持 4~8 路），代价可接受。

### 4.4 领域资产认知与 Nexent 数据流（可选）

```text
文档 / 表格 / 图片 / 事件 / 遥测 / 数据集
                    │
                    ▼
         知识资产（不可变版本）
                    │
                    ▼
  候选抽取 → 人工审核 → 本体发布
          │                 │
          └────────┬────────┘
                   ▼
     POST /knowledge/search（多跳路径 + 引用）
                   │
                   ▼
      决策轨迹（证据顺序 + 版本快照）
                   ▲
                   │ HTTP / MCP
          Nexent Agent + Skills
                   │
                   └── 可选：事件 / 工单 / 机器人执行接口
```

知识域的检索结果包含命中资产版本、本体节点、关系、跳数和引用片段；
决策记录再把这些证据按顺序固化下来。这样即使后续知识更新，历史结论仍能按
当时的资产版本和本体版本复核。Nexent 只通过 MCP 调用公开接口，不绕过后端
权限和审计边界。

## 五、核心业务流程：一次完整闭环

拿"马鼻码头拍到泡沫浮球碎片"举例，走一遍全链路：

### 第 1 步 · 边缘侧（毫秒~秒级）

```
摄像头 1080p@25fps
   │
   ├─► 抽帧（每 3 帧取 1 帧，降到 ~8fps，省算力）
   │
   ├─► YOLO11s 推理 → 原始检测框
   │      [{cls: foam, conf: 0.91, bbox: [412,288,468,331]}, ...]
   │
   ├─► ★ 时序校验（降误报第一道闸）
   │      目标级跟踪：类别相同 + 中心位移 < 60px + IoU > 0.25 → 认定为同一目标
   │      连续 3 帧命中同一目标 → 升级为「确认事件」
   │      浪花随机出现→命中数凑不满→被自然饿死
   │
   ├─► 上报节流（同一目标 90 秒冷却，避免刷屏）
   │
   └─► 组包 → MQTT publish QoS1
          topic: marine/lianjiang/CAM-MABI-01/event
```

**为什么必须做时序校验**：海面有两类高频干扰——浪花泡沫与阳光反光，两者在单帧上极像 EPS 泡沫。不做时序过滤时，模拟器可产生**每分钟上百条**原始干扰检测，平台会被淹没，操作员会直接关掉告警。加了时序校验后，仓库中已经复现两个不同输入集上的“时序链路误报抑制率”：

| 场景 / 指标 | 分子 / 分母 | 输入集 | 为什么不同 |
| --- | --- | --- | --- |
| **合成海面自检：76.0%** | `(599 条 fed - 144 条 absorbed) / 599 = 455 / 599 = 75.96%` | 200 帧合成海面自检：599 条原始检测，3 个确认事件 | 该合成流几乎全是瞬态噪声，稳定目标吸收的检测较少，时序过滤能消掉更大比例 |
| **模拟器三场景：42%~43%** | `suppressed / fed`；demo 为 `2451 / 5772 = 42.5%` | 模拟器 demo / stress / regression 的混合目标与噪声流 | 稳定目标贡献更多 `absorbed` 检测，噪声占比低于 76% 场景，因此抑制率较低 |

两者都定义为“被时序过滤的检测数 / 输入检测数”，不是检测 precision、recall、识别准确率或现场泛化精度。`76.0%` 来自 `edge/main.py` 运行期汇总与 `edge/detector/test_metrics.py`；`42%~43%` 来自 `edge/simulator/simulator.py`，三场景分别为 demo 42.5% / stress 41.9% / regression 42.8%。抑制率随噪声占比变化，当前独立测试集仍为空，感知评测结果为 `not_evaluated`。

### 第 2 步 · 平台入口（同步，<50ms）

`app/mqtt/handlers.py::handle_event` 被触发：

1. 报文按 `EventIngest` schema 校验（字段缺失直接丢弃并记日志）
2. 调 `EventService.ingest()`
3. **幂等判重**：查 `(device_id, seq)`。QoS1 会重复投递，判重是必需而非可选
4. 落库 `t_event`，状态 `new`
5. 调用方同步派单：高优先级事件提交后调 `_try_dispatch()`，
   `ingest(enqueue_dispatch=False)` 不再投 Redis Stream
6. WebSocket 广播 `new_event` → 大屏标红

HTTP 备用通道 `POST /events` 走同一套：`ingest(enqueue_dispatch=False)` +
提交后同步 `_try_dispatch()`，响应体里的 `task_id` 直接取本次派单产物。

### 第 3 步 · 派单决策（异步，百毫秒级）

`app/services/consumer.py::dispatch_consumer` 消费**显式入队**的事件
（`enqueue_dispatch=True` 的异步入口、批量补投），调
`DispatchEngine.dispatch_for_event()`：

```
① 防重复派单 ── 该 event 是否已有在途任务？有 → 跳过
      │
② 防抖合并 ──── 200m 内、10 分钟窗口内是否已有活跃任务？
      │          有 → 合并进去（机器人不必反复跑同一片水域）
      │          无 ↓
③ 可用性过滤 ── 在线 + 电量 ≥30% + 三仓总占用 <80%
      │
④ KNN 就近 ──── ST_DWithin 粗筛（走 GiST 索引）+ <-> 算子排序
      │
⑤ 类别加权 ──── 泡沫类任务顺路优先（减少空驶）
      │
⑥ 创建 t_task（状态直接 assigned）+ 事件状态改 dispatched
      │
⑦ MQTT 下发 robot/{robot_id}/task
      │
⑧ 等 ACK ────── 15 秒未确认 → 状态回退 pending，换下一台
```

**第 ②步为什么关键**：没有防抖时，同一片水域 3 分钟内报 10 条事件，就会派 10 趟——机器人来回跑，燃油/电量全耗在重复航路上。这是产品演示时最容易被看出来的"蠢"。

### 第 4 步 · 执行与回传

```
机器人收到派单
   ├─► 回 ACK  → robot/{id}/cmd/ack
   │      平台：task assigned → navigating
   ├─► 前往目标（周期回传遥测，QoS0）
   │      marine/lianjiang/RBT-001/telemetry
   │      平台刷新地图标记、电量、三仓占用
   ├─► 到达开始作业
   │      平台：navigating → collecting（记录 started_at）
   ├─► 作业完成，回传结果
   │      robot/{id}/task/progress
   │      {task_id, status: done, collected_weight: 12.5,
   │       review_result: confirmed, evidence_url: ...}
   └─► 平台：collecting → done（记录 finished_at）
          同步把 t_event.status 置为 resolved
          事件表 + 工单表 + 轨迹表 三处一致
```

### 第 5 步 · 数据沉淀

- `t_track` 按日分区记录轨迹点（每 5 秒一个点）
- 每日凌晨预聚合写入 `t_report_daily` 宽表
- 报表页只读宽表 → 事件量到百万级仍毫秒响应

## 六、关键架构决策记录

### 6.1 为什么用 Redis Streams 而不是数据库轮询

| 方案 | 问题 |
| --- | --- |
| 数据库轮询待派单事件 | 延迟高（受轮询间隔限制）、空转耗资源 |
| 同步调派单 | 机器人离线会阻塞 HTTP 请求/事件处理 |
| Kafka / RabbitMQ | 对小团队是过度设计，且 Redis 本来就要用 |
| **Redis Streams** | ✅ 消费者组 + ACK + pending list，消息不丢；零新增组件 |

Streams 相比 pub/sub 的关键优势：**有 ACK 与 pending list**。pub/sub 消息发出即忘，消费者崩了就永久丢；Streams 可以重投。

当前 HTTP/MQTT 两个事件上报入口都需要在响应/上行路径里同步拿到派单
结果，所以它们调用 `ingest(enqueue_dispatch=False)`，由提交后的
`_try_dispatch()` 直接派单，不再重复入队。Redis Streams 消费保留为
显式异步通道：未来新增「不需要同步 task_id」的入口、批量补投、或
外部投递事件时使用；数据库唯一约束 `uq_task_active_event` 仍作为
并发派单的最后兜底。

### 6.2 为什么对象存储用 MinIO

告警证据帧（每事件 1 张 JPEG，约 200KB）与作业影像属于**大文件、低频访问、需长期保留**。放数据库会让备份与迁移变得痛苦，放本地磁盘则没有生命周期管理。MinIO 提供 S3 兼容 API，未来迁云或换厂商成本接近零。

### 6.3 为什么流媒体用 go2rtc 而非 ZLMediaKit

| | go2rtc | ZLMediaKit |
| --- | --- | --- |
| 部署 | 单二进制，零依赖 | 需要配置 config.ini，模块多 |
| 上线耗时 | 5 分钟 | 半天 |
| 功能 | RTSP→WebRTC/FLV/HLS 够用 | 更全（录制、转码、集群） |

备赛阶段的目标是**跑通链路**，不是搭生产级流媒体集群。go2rtc 的配置是一份 YAML 加几个 stream 条目，任何人 5 分钟能加一路摄像头。

### 6.4 为什么 AI 推理服务独立进程

算法组与平台组的发版节奏完全不同：

- 平台组改一次派单逻辑 → 重启后端
- 算法组换一次模型权重 → 如果耦合，也要重启后端

独立成服务后，算法组可以热加载模型（`POST /infer/reload`）而不影响平台服务，平台组调接口时也不需要环境里有 onnxruntime 与 GPU 驱动。

**同时提供 stub 模式**：模型文件不存在时返回确定性的模拟结果（基于图片字节哈希），保证平台组在没有模型的情况下也能独立调试全链路。

### 6.5 为什么 WebSocket 之外还要 30 秒轮询兜底

WebSocket 只推**增量**。如果大屏网络抖动丢了 3 条 `new_event`，前端不会知道——它只是永远少这 3 条，且不会自愈。

所以前端 `App.vue` 里保留了 30 秒的 `refreshAll()` 轮询做全量对账。WebSocket 负责"快"，轮询负责"对"。

## 七、容错设计

| 失效点 | 后果 | 兜底机制 |
| --- | --- | --- |
| MQTT 断连 | 事件收不到 | 边缘盒本地队列缓存（上限 1000 条），恢复后按原 seq 补传 |
| 边缘盒崩溃 | seq 归零导致判重误杀 | seq 持久化到本地文件，重启后从上次值续上 |
| 机器人孪生/机载单元重启 | 遥测 seq 从 0 重来，平台 `(device_id, seq)` 判重误杀 | 设备序号跨进程持久化（`edge/device_sim`，WP-14E：路径可配置，**默认不写盘**；原子写，重启后严格单调递增，不回退/不重用） |
| 平台重启 | ACK 判重水位（进程内内存）丢失 | 启动时从 `t_task_ack` 自动重建（WP-14E，见下「启动恢复」） |
| MQTT 重复投递 | 重复派单 | `(device_id, seq)` 唯一约束 + 应用层预查 |
| Redis 不可用 | 派单队列失效 | 事件仍入库；`pending_dispatcher` 每 30 秒扫表补派 |
| 机器人 ACK 超时 | 任务卡在 assigned | 15 秒超时回退 pending，重新选车 |
| 无可用机器人 | 事件积压 | 事件保持 `new`，机器人上线后定时补派 |
| 消费处理异常 | 消息丢失 | 不 ACK（留在 pending list）或进死信 stream |
| 数据库断连 | 服务不可用 | `pool_pre_ping` 提前剔除坏连接 + `pool_recycle=3600` |
| 前端丢消息 | 大屏数据不全 | 30 秒全量轮询对账 |
| 地图 SDK 加载失败 | 地图空白 | 内联 SVG 兜底 + 降级为列表视图 |

**启动恢复（WP-14E，ACK 判重水位）**：平台 `AckTracker` 是进程内内存表，
进程重启后其「已受理回执」与「设备 ACK 水位」会丢失。后端 lifespan 启动
阶段在 MQTT 客户端可用后，自动调用
`TaskAckRepository.rebuild_ack_tracker(mqtt_client.ack_tracker)` 从审计账本
`t_task_ack` 重建：

- **降级不失败**：数据库不可用 / 表不存在 / 查询异常 → warning 并继续
  启动，绝不让启动失败（与 lifespan「每步独立 try」的降级风格一致）；
- **幂等**：重复启动不叠加、不报错；
- **耗时上界**：整个重建包在超时（默认 5s）内，超时即降级，绝不让启动
  无限期挂起；
- **可观测**：结果（行数 / 耗时 / 是否降级）经 `/health` 顶层
  `ack_recovery` 字段与日志暴露，不静默。

**恢复边界（如实声明，不宣称完整恢复）**：`duplicate` / `out_of_order`
判定重启后可恢复（规范回执 + 设备 ACK 水位来自账本）；但 **`late` 判定对
「发布后未 ACK」的命令重启后仍不可恢复** —— `late` 依赖发布时登记的
`expires_at`，而 `t_task_ack` 不保存该字段（内存登记表固有边界）。即便不
重建，账本以 `command_id` 为准 + 任务状态机守卫仍保证重复回执不重复推进。

## 八、性能与容量规划

### 8.1 数据量估算（单县规模）

| 对象 | 估算 | 依据 |
| --- | --- | --- |
| 摄像头 | 20 路 | 连江主要沿海点位 |
| 每路日均确认事件 | ~40 条 | 加了时序校验后的实测值 |
| 日均事件总数 | ~800 条 | 20 × 40 |
| 年事件总量 | ~29 万条 | 800 × 365 |
| 每事件证据帧 | ~200 KB | 1080p JPEG q85 |
| 年影像存储 | ~58 GB | 29 万 × 200KB |

结论：**单机 PostgreSQL 完全够用**，不需要分库分表。只有 `t_track` 会因为机器人高频回传而膨胀，所以按日分区。

### 8.2 热点查询与对策

| 查询 | 频次 | 对策 |
| --- | --- | --- |
| 大屏指标卡 | 每 30 秒 | 简单 COUNT，索引覆盖 |
| 热力图聚合 | 每 60 秒 | `ST_SnapToGrid` 投影到 3857 + GiST 索引 |
| 就近派单 | 每事件 | `ST_DWithin` 粗筛 + `<->` KNN 算子 |
| 报表查询 | 低频 | 只读预聚合宽表 `t_report_daily` |

**热力图的两个坑**（已在本项目中规避）：

1. **必须投影到 3857（米制）**：`ST_SnapToGrid` 若作用在 4326 上，网格边长单位是"度"——在 26°N 附近，1 度经度约 100km，网格会大得毫无意义。
2. **返回密度而非总数**：否则大网格天然比小网格"热"，热力图会失真。所以返回 `count / (grid_size²)` 的个/m²。

## 九、安全与合规

| 项 | 措施 |
| --- | --- |
| 传输加密 | 生产环境全站 HTTPS（WSS）；MQTT 走 TLS（8883） |
| 密码存储 | bcrypt（cost=12），不存明文 |
| 令牌 | HMAC-SHA256 签名载荷，含 `exp` 过期时间 |
| 权限模型 | admin（全部）/ operator（本辖区写）/ approver（仅 Agent 人工审批）/ viewer（只读） |
| 设备隔离 | EMQX ACL 按 clientid 前缀授权，设备只能发自己主题 |
| 敏感配置 | 全部走环境变量，`.env` 已在 `.gitignore` 排除 |
| 地图合规 | 使用腾讯地图（国内持牌服务商）；SDK 走 `_TMapSecurityConfig` 代理模式，**不在前端嵌入任何密钥** |
| 数据合规 | 人脸等敏感信息在边缘侧即脱敏（不存储原始视频，只存垃圾证据帧） |
