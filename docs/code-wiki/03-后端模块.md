# 03 · 后端模块（backend/）

> Python 3.11 + FastAPI，异步全栈。入口 `app.main:app`，开发模式 `make dev-backend`（uvicorn :8000 热重载）。

## 1. 分层架构与请求流

```
HTTP 请求
 → middleware/response.py   trace_id 中间件（每请求生成 trace_id）
 → api/v1/*.py              路由层（只做编排：参数校验 + 调 service + 组装响应）
 → services/*.py            业务逻辑层（派单引擎、状态机规则、领域校验）
 → repositories/            数据访问层（SQLAlchemy 查询、PostGIS 空间运算）
 → models/*.py              ORM（表定义 + 领域常量 + 状态机）
 → PostgreSQL
响应统一信封: {code, data, message, trace_id}   由 register_exception_handlers 保证
```

分层铁律：API 层不写业务逻辑，Service 层不写 SQL，所有状态变更必须走 services 层（禁止直接 UPDATE 任务状态）。

## 2. 启动流程（app/main.py）

`lifespan` 按序启动，关闭时逆序释放：

1. **事件循环策略**：Windows 上必须切 `WindowsSelectorEventLoopPolicy`（aiomqtt 依赖 add_reader，Proactor 不支持——否则 MQTT 永远连接超时）
2. 初始化日志（loguru）
3. 连接 Redis
4. 启动 MQTT 订阅（`app/mqtt/client.py` 的 `mqtt_client`）
5. **ACK 判重水位恢复**（`recover_ack_tracker`，WP-14E）：从 `t_task_ack` 重建 AckTracker，5 秒超时上界，失败降级继续启动，结果写 `app.state.ack_tracker_recovery` 供 `/health` 观测
6. 启动派单消费者（Redis Streams）
7. 启动定时任务（补派 `pending_dispatcher`、报表聚合）

`create_app()` 挂载：`/docs` OpenAPI、CORS、trace_id 中间件、异常处理器、`/api/v1` 前缀的 `api_router`。

## 5. 数据模型层（app/models/）

### 5.1 核心三表（业务主链路）

**Event（t_event）** — `models/event.py`
- 常量类 `WasteClass`：FOAM/PLASTIC/FISHING_GEAR/OTHER 四类，`HIGH_PRIORITY=(FOAM, FISHING_GEAR)` 触发紧急优先级
- `EventStatus`：NEW → DISPATCHED → RESOLVED / IGNORED
- 字段：`event_id`(业务ID)、`device_id`+`seq`（**唯一约束**，杜绝 MQTT 重传重复派单）、`location`(PostGIS POINT 4326)、`main_class`、`max_confidence`、`evidence_url`、`township`（入库时 `nearest_township` 最近邻算好落字段，辖区过滤走索引）
- 索引：location GiST、(event_time, main_class) 复合

**Task（t_task）** — `models/task.py`
- `TaskStatus` 状态机：`TRANSITIONS` 字典 + `can_transition()`；ASSIGNED 可回退 PENDING（ACK 超时重派）；DONE/CANCELLED 终态
- `TaskPriority`：**优先级唯一真源**，`for_waste_class()` 按 `WasteClass.HIGH_PRIORITY` 给 URGENT(1)/NORMAL(3)，禁止任何地方再写字面量
- `ReviewResult`：到场复核结论（confirmed/not_found/recheck）

**Device（t_device）** — `models/device.py`
- `DeviceType`：shore_camera / drone / robot
- `DeviceStatus`：online / offline / fault；`location` GiST 索引支撑就近派单 KNN
- `meta` JSONB 存电量、仓容等扩展属性

另有 **t_track** 机器人遥测轨迹表（按日分区，`db/partitions.py` 写入路径自愈补分区 + `deploy/postgres/ensure_track_partitions.sql` 运维兜底）和 **t_report_daily** 每日聚合报表表。

### 5.2 Agent 运行契约五表（models/agent*.py）

| 表 | 模型 | 职责 |
| --- | --- | --- |
| t_agent_run | `AgentRun` | 一次运行：状态机、请求、摘要 |
| t_agent_step | `AgentStep` | 运行步骤轨迹（plan/replan 只追加不覆盖） |
| t_agent_memory | `AgentMemory` | 运行记忆（只存摘要与业务理由） |
| t_agent_approval | `AgentApproval` | WRITE 工具人工审批记录 |
| t_agent_run_state | `AgentRunState`（agent_state.py） | 持久化续跑状态（WP-10） |

配套枚举：`AgentRunStatus`（运行级）、`AgentStepStatus/AgentStepType`、`AgentRiskLevel`、`AgentDecision`、`AgentErrorCode`、`AgentMemoryType`、`AgentScopeType`、`AgentSourceType`。

### 5.3 知识域八表（models/knowledge.py）

- 资产：`KnowledgeAsset` + `KnowledgeAssetVersion`（版本不可变，`KnowledgeAssetType` 多模态类型、状态枚举）
- 本体：`OntologyVersion`（候选→审核→发布状态机）+ `OntologyNode` + `OntologyRelation`（`OntologyReviewStatus` 人工审核）
- 决策：`DecisionTrace` + `DecisionEvidence`（证据顺序、资产/本体/策略版本绑定）

### 5.4 其他

- `TaskAck`（t_task_ack）：ACK 审计账本（WP-14D），`TaskAckRepository.rebuild_ack_tracker()` 支撑启动恢复
- `ChatSession` / `ChatMessage`（t_chat_*）：对话助手会话持久化

## 6. 数据访问层（app/repositories/）

每表一个 Repository（`DeviceRepository` / `EventRepository` / `TaskRepository` / `TaskAckRepository` 等），方法返回**显式类型**。历史缺陷教训已固化为守卫：`list_tasks` 返回 `tuple[list[Task], int]`，调用不解包就下标访问会被 `check_events_selftest` 的扫描器全工程抓出（「方法返回 tuple 却被当单值用」模式一律报出）。

## 7. 业务服务层（app/services/）

### 7.1 dispatch.py — 派单引擎（平台最核心）

- `DispatchEngine.dispatch_for_event()`：主入口——去重、防抖合并、五步筛选选机器人、创建任务、标记事件，返回 `Task | None`（**每个出口必须显式 return**，由 AST 守卫钉死）
- `finalize_dispatch(task)`：**派单成功唯一收尾出口**（MQTT 下发 + WebSocket 推送 4 字段契约），四个派单入口全部调用
- `reassign_task()`：ACK 超时回退 + 换车重派闭环
- `_parse_point()`：内存解析 EWKT/EWKB 坐标（不再发 `SELECT ST_X()`——历史写法缺 where 会取到全表第一行坐标，把机器人派去别人的目标点）
- `_class_match_weight()`：类别匹配加权（顺路复用），结构性断言保证「同一事件配不同机器人状态时权重必须不同」

### 7.2 consumer.py — Redis Streams 消费者

- `dispatch_consumer`：`xreadgroup(">")` 读新消息派单
- **PEL 回收**：读新消息前先 `xautoclaim` 认领挂起超 60 秒的条目（Redis Streams「不 ACK 就必须有人认领」的经典坑：不认领则永不重投 + 内存泄漏）；已被补派处理的历史欠账直接 ACK
- `pending_dispatcher`：定时补派 pending 任务（调 `finalize_dispatch`）

## 10. AI 推理服务（app/services/ai/server.py）

独立进程（`backend/Dockerfile.ai`，容器 `ai-service:8081`，依赖仅 `requirements-ai.txt`：onnxruntime + pillow + opencv-headless，便于独立部署到 Jetson/RK3588）：
- 加载 `ml/models/best.onnx`（`AI_MODEL_PATH`），letterbox 缩放（PIL，非 opencv——曾因漏列 Pillow 依赖线上 ImportError）
- NMS 后处理支持**两种模型输出格式**（原生 / EfficientNMS baked）——曾只支持一种，换导出格式就 ValueError 而测试全绿，现由 `tests/test_ai_postprocess.py` 用构造张量覆盖真实形状
- 证据帧画框返回；纯 CPU 可跑，GPU 注释可开

## 11. 数据库与迁移

**双轨制**（改表前必读，详见 [08-部署与运行](./08-部署与运行.md)）：
- 轨道 A：初始建表 `backend/db/init/01_schema.sql`（PostGIS 扩展、分区表、触发器，容器首启自动执行）；02_seed.sql 演示种子；03_seed_knowledge_demo.sql 知识演示数据
- 轨道 B：增量变更 Alembic（唯一主配置 `backend/alembic.ini`，**必须纯 ASCII**——中文 Windows cp936 解码会让所有迁移命令崩溃）
