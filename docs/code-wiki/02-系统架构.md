# 02 · 系统架构

## 1. 五层架构

```
┌──────────────────────────────────────────────────────────────┐
│  展示层  实时监测大屏 · 热力图 · 工单看板 · 报表中心 · 智能助手   │  frontend/
├──────────────────────────────────────────────────────────────┤
│  应用层  事件服务 · 派单引擎 · 统计服务 · 报表服务 · 用户权限    │  backend/app/api + services
├──────────────────────────────────────────────────────────────┤
│  智能层  AI 推理服务（检测/分类）· 时序校验 · 误报过滤           │  backend/app/services/ai + edge/detector
├──────────────────────────────────────────────────────────────┤
│  数据层  PostgreSQL(PostGIS) · Redis · MinIO(对象存储) · MQTT  │  docker compose 基础设施
├──────────────────────────────────────────────────────────────┤
│  接入层  RTSP 流接入 · 边缘盒上报 · 机器人 MQTT 上行 · 无人机   │  edge/ + go2rtc + EMQX
└──────────────────────────────────────────────────────────────┘
```

**一个关键工程判断**：视频流不经过边缘盒——边缘盒**旁路取流**做推理，避免算力被转发挤占。摄像头 RTSP 直接送 go2rtc 转成 WebRTC/FLV 给前端；边缘盒自己拉同一份流做检测。

## 2. 四条数据流

| 数据流 | 方向 | 协议 | 载体 |
| --- | --- | --- | --- |
| 视频流 | 摄像头 → go2rtc → 前端 | RTSP → WebRTC/FLV | `deploy/go2rtc/go2rtc.yaml`，前端 `VideoPlayer.vue`（mpegts.js） |
| 检测事件流 | 边缘盒 → 平台 | MQTT QoS1 | `marine/{site}/{device}/event` → `app/mqtt/handlers.py` |
| 调度指令流 | 平台 → 机器人 | MQTT QoS1 | `robot/{robot_id}/task` → ACK 回执 `robot/{id}/cmd/ack` |
| 作业回传流 | 机器人 → 平台 | MQTT + 对象存储 | `robot/{robot_id}/task/progress` + MinIO 作业影像 |

MQTT 主题树是静态契约（3~4 层，变量放 payload），统一定义在 [backend/app/mqtt/topics.py](../../backend/app/mqtt/topics.py) 的 `Topics` 类，规范全文见 `docs/mqtt-topics.md`：

```
marine/{site_id}/{device_id}/event         垃圾检测事件   QoS1
marine/{site_id}/{device_id}/telemetry     心跳/电量/仓容 QoS0
marine/{site_id}/{device_id}/status        online/offline retained QoS1（LWT 遗嘱）
marine/{site_id}/{device_id}/cmd           下发指令(云→边) QoS1
marine/{site_id}/{device_id}/cmd/ack       指令回执        QoS1
robot/{robot_id}/task                      派单下发        QoS1
robot/{robot_id}/task/progress             作业回传        QoS1
robot/{robot_id}/cmd/ack                   任务确认        QoS1
```

## 3. 核心业务闭环（感知 → 决策 → 执行 → 回传）

```
┌──────────┐  MQTT   ┌─────────────┐         ┌──────────────┐
│ 边缘盒    │ ──────→ │ 事件入库     │ ──────→ │ 派单引擎      │
│ cv检测+时序│ event  │ t_event     │ Streams │ DispatchEngine│
└──────────┘         └─────────────┘         └──────┬───────┘
                                                  │ 五步筛选
     ┌────────────┐  WebSocket   ┌──────────┐      │ 选定机器人
     │ 前端大屏    │ ←─────────── │ 工单创建  │ ←────┘
     │ task_update │  ws/alerts  │ t_task   │
     └────────────┘             └────┬─────┘
                                     │ MQTT robot/{id}/task
                                ┌────▼─────┐
                                │ 机器人    │ ── ACK → 状态机 assigned
                                │ 执行作业  │ ── progress → navigating/collecting/done
                                └──────────┘
```

### 3.1 感知端（edge/）

`edge/main.py` 的 `EdgeRuntime` 主循环：取流（synthetic/camera/RTSP/视频文件）→ `CvDetector.detect()`（背景建模 ∪ 颜色通道 → 轮廓 → 规则分类）→ `TemporalValidator`（单帧不确认，连续命中才产生事件）→ 上报节流 → MQTT 发布。详见 [05-边缘与算法模块](./05-边缘与算法模块.md)。

### 3.2 决策端（backend dispatch）

事件进入平台有**两条入口、四个派单出口**：

- 事件入口 ①：HTTP `POST /api/v1/events`（同步尝试派单）
- 事件入口 ②：Redis Streams `stream:events` 消费者（异步派单）
- 派单出口 ①②③④：HTTP 同步派单 / Streams 消费者 / 定时补派 `pending_dispatcher` / 手动补派 API `assign_pending_tasks`

**四个出口全部收敛到唯一收尾函数 `finalize_dispatch(task)`**（`app/services/dispatch.py`）：下发 MQTT 指令 + 推送看板 WebSocket。这是从「补派只建任务不下发指令」的历史缺陷中总结出的架构约束，由 `tests/test_dispatch_finalize.py` 用 AST 穷举守卫。

派单引擎五步筛选：
1. 可用性过滤（在线 / 电量 ≥ `dispatch_min_battery` / 仓容 ≤ `dispatch_max_bin_usage`）
2. 距离排序（KNN，搜索半径 `dispatch_range_meters`）
3. 类别匹配加权（顺路复用：候选机器人当前在途任务类别与事件类别相同的加权）
4. 选中下发（MQTT + 等 ACK，超时 `dispatch_ack_timeout_seconds`）
5. ACK 超时处理（回退 pending → 换车重派 `reassign_task`）

防抖：同网格区域 `dispatch_merge_radius_meters` 米内、`dispatch_merge_window_minutes` 分钟窗口的多个事件合并为一个任务。

### 3.3 状态机（单一真源）

```
任务:  pending → assigned → navigating → collecting → done
       任意态 → cancelled；assigned → pending（ACK 超时回退重派）
事件:  new → dispatched → resolved / ignored
```

定义在 `app/models/task.py` 的 `TaskStatus.TRANSITIONS`——所有状态变更必须走 services 层，禁止直接 UPDATE；非法迁移由 `tests/test_state_machine.py` 守卫。

### 3.4 数据回流

- 机器人 `task/progress` 上报 → `mqtt/handlers.py` 状态映射 → 更新 `t_task` + WebSocket 推送
- 完成工单的打捞量由操作员录入（不用随机数造假）
- `services/report.py` 每日聚合任务把事件/工单明细 UPSERT 进 `t_report_daily`，报表"必须会涨"

```
                    └────────────────────────────────────┘
   边缘盒/模拟器 ──→ │ EMQX :1883 (MQTT) :18083 (面板)    │ ←── backend mqtt client
                    └────────────────────────────────────┘
┌─────────┐  HTTP   ┌────────────────────────────────────┐
│ frontend│ ──────→ │ backend :8000 (uvicorn --reload)    │
│ :5173   │  WS     │  ├─ lifespan: Redis→MQTT→ACK恢复    │
│ (vite)  │ ←────── │  │   →消费者→定时补派/报表           │
└─────────┘         │  └─ /api/v1/* 14 路由               │
                    └───┬────────────┬────────────┬──────┘
                        │            │            │
                 ┌──────▼──┐  ┌─────▼─────┐  ┌──▼──────────┐
                 │postgres │  │ redis :6379│  │ ai-service  │
                 │+PostGIS │  │ Streams    │  │ :8081 ONNX  │
                 │:5432    │  └───────────┘  └─────────────┘
                 └─────────┘         ┌──────────────┐
                    │                │ minio :9000   │ (minio-init 建 bucket)
                    └── init 脚本 ──→└──────────────┘
```

8 个服务：`postgres`（postgis/postgis:14-3.3，首启自动执行 `backend/db/init/`）、`redis:7-alpine`、`emqx:5.8`（bootstrap.csv 导入认证与 ACL）、`minio` + 一次性 `minio-init`（建 `events` bucket）、`go2rtc`、`backend`（热重载挂载源码 + 只读挂载 `edge/` 与 `artifacts/agent_evals/`）、`ai-service`（Dockerfile.ai 独立镜像）、`frontend`（dev target）。生产另有 `frontend-prod`（nginx 托管静态产物，`--profile prod` 显式启用）。

**挂载细节的 why**（写错过的地方）：
- `./edge:/edge:ro`——后端有 3 处 `from edge.detector.detector import CvDetector`，而 backend 构建上下文只有 `./backend`，靠 `Path(__file__).parents[4]` 反推仓库根定位
- `./artifacts/agent_evals:/artifacts/agent_evals:ro`——没有它，`/api/v1/agents/evals/latest` 永远返回 6008，前端质量雷达一直空态

## 5. 智能体架构（决策大脑）

### 5.1 Agent Runtime（确定性内核）

`app/services/agents/runtime.py` 的 `AgentRuntime`——**不依赖数据库 / Redis / MQTT / 外网 / 大模型**即可运行：

```
运行状态机:
created → planning → waiting_policy → waiting_approval
        → executing → observing → verifying
        → succeeded | failed | cancelled | expired（终态不可迁移）
```

- **确定性控制器**负责状态、规则、工具调用、超时、重试和终止（`runtime.py`）
- **规则策略**先给出可验证的基线决策：`RulePlanner` + `DEFAULT_RULE_PLAN`（`planner.py`）、`RulePolicyGuard`（`policy.py`）
- **大模型仅作可选增强**：`ModelAdapterPlanner` + `OpenAICompatibleModelClient`（`model_adapter.py`），模型不可用自动退回规则模式，核心能力不下降
- **WRITE 工具可要求人工审批**：`AGENT_REQUIRE_APPROVAL_FOR_WRITE` 开关，approver 角色决定（`approval` 流程 + `repositories.py`/`persistent_repository.py` 仓储）
- **跨 run 经验**：`LessonStore`（`lessons.py`）沉淀命中经验
- 轨迹只写 decision_summary 与 input_hash/output_hash（解密预算：不保存模型私有思维链）

### 5.2 对话助手（assistant/）

`services/assistant/engine.py` + `tools.py`：规则兜底 + OpenAI-compatible LLM + 最多 `assistant_model_max_tool_rounds` 轮工具编排；支持拖图检测（复用 CvDetector）、会话持久化（`t_chat_session`/`t_chat_message`）。

### 5.3 知识智能体（knowledge）

`services/knowledge.py` 的 `KnowledgeService`（约 1600 行，平台横向能力，不依赖机器人）：
- 多模态资产统一登记：文档/表格/图片/事件/遥测/数据集，版本不可变（`content_digest` 摘要）
- 动态本体生命周期：候选抽取（`extract_term_candidates` / `cooccurrence_relations`）→ 人工审核 → 发布，发布版本证据可追溯
- 跨文档多跳检索：`relation_paths` + `score_document`，返回节点/关系/路径/片段与引用
- 决策链路溯源：`DecisionTrace` + `DecisionEvidence` 保存证据顺序、资产/本体/策略版本

## 6. 实时推送链路

```
业务变更(派单/状态/事件/遥测)
   → app/ws/manager.py  ws_manager.push_*()
   → WebSocket /api/v1/ws/alerts?token=...
   → frontend/utils/realtime.js (心跳/断线/指数退避重连)
   → stores/realtime.js (Pinia 分发给大屏/事件/工单/设备各页)
```

推送负载是**手工拼装的 dict，契约由常量声明**，`tests/test_ws_contract.py` 用 AST 静态扫描每一处推送调用的字面量键集合，新增推送点自动纳入校验。

## 7. 健康与降级语义

`/health` 如实返回依赖状态（`degraded` / `down` 而非谎报 `ok`），由 `tests/test_health_degradation.py` 守卫——裸机模式没有 Docker 依赖时，这是设计行为不是 bug。生产配置在启动时由 `validate_production_settings()` 强制 fail-closed（占位密码 / DEBUG=true / CORS `*` 直接拒绝启动）。
